Training on a server

Clone the project on a rented server, train there, keep the model out of git, and bring the weights home to test. Code travels by git; weights travel by rsync; the training set travels nowhere.

1The shape of it ↑

Three facts make this simple:

  • Training needs nothing but Node — no npm install on the server. The trainer and the data factory are dependency-free.
  • The dataset does not exist as files — it is drawn from seeds. The same seed on both machines gives the same bytes, so nothing to sync.
  • Weights are data, not source — they are gitignored and travel directly to you.

2Set up the server, once ↑

Any CPU droplet with 4–8 vCPU will do; the model is small and the trainer uses the CPU. On the laptop, put the branch on GitHub first.

# on your laptop
git push -u origin omr

# on the server
ssh user@server
git clone https://github.com/Guseyn/MuSemantiQ.git
cd MuSemantiQ
git checkout omr
node -v                     # v22 or newer — nothing else is needed

3A training run ↑

git pull                                        # the latest code

tmux new -s train                               # the run survives your ssh session
node src/omr/training/train.js \
  --out=src/omr/model/weights.json | tee run.log

# from another ssh session, any time:
tail -f run.log                                 # one line per epoch

The run prints a line per epoch — loss, training accuracy, validation accuracy — and writes model/weights.json with its sha256 at the end. Ctrl-b d detaches tmux, tmux attach -t train returns.

Reproducible The seeds live in the run itself: the same code and seed give the same dataset and the same weights on any machine. The seed and shape are in runTraining() in src/omr/training/train.js.

4Model data stays out of git ↑

Already in .gitignore, on both machines alike:

# The trained model and its runs: generated on the training server and copied
# home by hand. The dataset is not here at all — seeds regenerate it.
# Weights are data, not source.
src/omr/model/weights.json
src/omr/model/checkpoints/
training-data/

So git status on the server stays clean while a run lives in model/, and a weights file can never be committed by accident.

5Bring the model home ↑

rsync -av server:~/MuSemantiQ/src/omr/model/ ./src/omr/model/
rsync -av server:~/MuSemantiQ/run.log ./              # optional: the loss history

shasum -a 256 src/omr/model/weights.json              # must match the sha the trainer printed

The trainer hashes exactly the bytes it wrote, so a mismatch means a broken transfer or a different run — re-rsync before trusting the file. Once the weights are in src/omr/model/, the code picks them up where you load them (see below).

6Test it locally ↑

npm run test:omr:all

The suite runs without the weights — rules and math are tested against drawn pages. To hear the transferred model speak, load it and ask it about a few crops:

# node --input-type=module -e "…paste this…"
import { readFileSync } from 'node:fs'
import { modelFromWeights } from '#msq/omr/training/exportWeights.js'
import classifyComponent from '#msq/omr/analysis/classifyComponent.js'
import { generateTrainingSet } from '#msq/omr/training/generateTrainingSet.js'

const { shape, layers } = JSON.parse(readFileSync('src/omr/model/weights.json', 'utf8'))
const model = modelFromWeights({ shape, layers })
const { classIds, samples } = generateTrainingSet({ seed: 1, samplesPerClass: 1, gridSize: shape.gridSize })
for (const sample of samples) {
  const answer = classifyComponent(model, sample.pixels, classIds)
  console.log(sample.classId, '→', answer.className, answer.confidence)
}
Class order matters The model's classes are the order it was trained with. Both sides use generateTrainingSet defaults, so they match; a trained-on-purpose run should carry its classIds alongside the weights.

7Cheat sheet ↑

# laptop — publish the branch
git push -u origin omr

# server — first time
git clone https://github.com/Guseyn/MuSemantiQ.git && cd MuSemantiQ
git checkout omr

# server — every run
git pull
tmux new -s train
node src/omr/training/train.js --out=src/omr/model/weights.json | tee run.log
# … wait, or Ctrl-b d and come back …
tail run.log

# laptop — take the result
rsync -av server:~/MuSemantiQ/src/omr/model/ ./src/omr/model/
shasum -a 256 src/omr/model/weights.json
npm run test:omr:all

Release weights come from one machine — different CPUs can round floats in the last decimal — and the printed hash is what pins the result. Once a weights.json is adopted, it never moves silently.
