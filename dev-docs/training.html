Training on a server

Freeze the code, documentation, data and configuration; train symbol and text models on a rented server; bring both artifacts home and verify the combined candidate. You drive the remote work from your laptop over ssh. Weights stay out of git and are always passed by path.

1The shape of it ↑

Four rules keep a run reviewable:

  • Freeze first. Choose one commit after the code and documentation are finished. Do not change the renderer, training data, configuration or docs while that candidate is being trained and verified.
  • Train two classifiers. The symbol artifact classifies notation blobs. The nested ocr artifact reads titles, subtitles, instrument titles, page metadata and unit text, including dynamics and chord letters.
  • Generated data has an identity. Seeds regenerate crop datasets. A full-page bundle also records each PNG, canonical target, style, mutation and SHA-256, with composition-level train / validation / test splits.
  • Weights are candidates, not source. There is no fallback model. The CLI, verifier and legacy OMR tests all need an explicit artifact.

2Set up the server, once ↑

A CPU server with Node 22 or newer is enough; both trainers are plain Node and use no training framework. Check out the project and its font files there, then check the version from your laptop:

ssh user@server 'cd MuSemantiQ && node -v'

The tracked helpers in remote-training-scripts/ handle upload, training, download and verification. Your host stays in one config file, not in every command. The default requires a clean frozen commit; the prepare script uploads that checkout rather than a moving branch.

From this point until verification ends, a source or documentation change means a new freeze and a new candidate, not a quiet continuation of the old run.

3Freeze, then train ↑

3.1 Run the pre-training tests

Before starting remote work, test the renderer, audio, serializer and generated walkthroughs. These tests do not load OMR weights:

npm run test:pretraining

Record the commit used for this green run. It is the <frozen-commit> in every later step.

3.2 Freeze the full-page evidence

Generate the remote bundle from the same checkout. It contains complete rendered pages at 0.5×, 0.75×, 1×, 1.5×, 2× and 3×, their unmutated canonical page schemas, source SVG geometry, text targets and a manifest of hashes. The six-language title/subtitle corpus is included as full pages with its own composition-level splits:

Set the remote host and paths once in remote-training-scripts/config.sh, then run:

npm run omr:remote:prepare

The script runs the pre-training checks, generates the bundle with the current commit hash, uploads the frozen checkout with rsync, and leaves training-data/remote-bundle/manifest.json on the server. It refuses a dirty checkout unless you deliberately set OMR_ALLOW_DIRTY=1.

The generator balances 40 style presets — 20 definitions in both Bravura and Leland — and cycles through the clean, screenshot, scan-light, scan-medium and scan-hard mutation profiles. Local stave spacing, line thickness, stave gaps and page-line gaps vary independently. A composition receives one split before any of its pages or variants are drawn, so two versions of one work cannot leak into different splits.

The bundle freezes full-page evidence; it does not claim recognition accuracy. It also carries in-context symbol crops with unambiguous renderer labels. The symbol trainer adds isolated renderer crops for shared-target classes and generates fresh crop degradation per epoch; the OCR trainer generates character crops.

3.3 Train the symbol model remotely

Run the symbol trainer against the frozen bundle. The script uploads the checkout if needed, starts the remote run, downloads its log, history and manifest, and leaves the symbol artifact in the configured run directory:

npm run omr:remote:train

The composition split is already frozen. Training reads only the train partition and validates on validation; test, including Allegro Burlesco, remains untouched until candidate verification. The flags select a candidate's shape and data, not an accuracy guarantee.

3.4 Train the six-language OCR model remotely

The same omr:remote:train command also starts the OCR run from the frozen checkout. It writes best-weights.json, history.json, manifest.json and training.log in the configured OCR run directory:

npm run omr:remote:train

The alphabet covers English, French, German, Italian, Spanish and Russian, with accented Latin and Cyrillic characters, digits, punctuation and typographic spaces. Training uses the renderer's own Noto Serif, Noto Sans, Gentium Plus and Gothic A1 glyph paths, at several sizes and scales. Dynamic and chord-letter targets are extracted from the page schema; no dictionary or spelling stage repairs an uncertain character.

Implemented is not verified These commands and data paths are implemented. Do not publish a weight-based accuracy claim until a named combined candidate has passed candidate verification and you have read its remaining differences and uncertainties.

4Model data stays out of git ↑

The generated bundle, run logs and candidates live under training-data/, which is gitignored. The old optional adopted path is ignored too:

src/omr/model/weights.json
src/omr/model/checkpoints/
training-data/

Keep using explicit paths instead of relying on that old path. A combined candidate has the symbol model at the top level and the complete text model under ocr:

{
  "shape": { … },
  "layers": { … },
  "classIds": [ … ],
  "ocr": {
    "shape": { … },
    "layers": { … },
    "classIds": [ … ]
  },
  "metadata": {
    "type": "mu-semanti-q-omr-candidate",
    "version": 1,
    "symbolSha256": "…",
    "ocrSha256": "…"
  }
}

A symbol-only artifact can run, but visible text then produces OCR uncertainties. Combining validates both model shapes and requires the OCR class order to match the six-language alphabet exactly.

5Bring both artifacts home and combine them ↑

Download both runs and combine them without changing either model. The script checks the artifact shapes and records both source hashes:

npm run omr:remote:download

The metadata records both source hashes. Pass training-data/candidates/combined.json to every later check; do not replace it halfway through verification.

6Verify the candidate locally ↑

The canonical verifier rasterizes complete visual fixtures at all six scales, translates each page with the named candidate, parses the generated MSQ again, and compares visible page-schema fields and custom styles. Editor reference IDs and playback-only settings are outside that comparison. A case is accepted only when the visible schemas and styles are equal and both report.uncertain and report.ignored are empty.

npm run omr:verify -- \
  --weights=training-data/candidates/combined.json \
  --scales=0.5,0.75,1,1.5,2,3 \
  --out=training-data/verification-failures

The default fixture set is a small first check. Use --all for every Bravura visual fixture, --fixture-font=leland for the Leland fixtures, or --fixtures=chords-basics,rhythm-rests for a named subset. The JSON output separates semantic and style mismatches, parser errors, uncertain symbols and ignored ink; --out keeps failed MSQ and diagnostics for inspection.

Then verify the frozen bundle itself, including every style preset, local-geometry variant and degradation profile:

npm run omr:verify:remote -- \
  --weights=training-data/candidates/combined.json \
  --data=training-data/remote-bundle/manifest.json

The legacy OMR suite has its own explicit requirement. Set OMR_WEIGHTS to the same candidate:

OMR_WEIGHTS=training-data/candidates/combined.json npm run test:omr:all

Without OMR_WEIGHTS, that suite stops rather than substituting a model. This is separate from npm run test:pretraining, which needs no weights.

What the result means

Validation loss and crop accuracy describe their own samples. Canonical verification describes complete renderer fixtures. Neither is a real-book accuracy measurement. Real books and hand-corrected real-page labels are deferred; do not turn a synthetic pass into a claim about scans or photographs.

The main API takes the artifact explicitly as well:

# node --input-type=module -e "…paste this…"
import { readFileSync, writeFileSync } from 'node:fs'
import { decodeImageToGrayscale, translateImageToMsq } from '#msq/omr/api.js'

const weights = JSON.parse(readFileSync(
  'training-data/candidates/combined.json', 'utf8'
))
const image = decodeImageToGrayscale(readFileSync('score.png'))
const { msqText, report } = translateImageToMsq(image, { weights })

writeFileSync('score.msq', msqText)
console.log(report.uncertain)

For a project, translateImagesToMsqPages(images, { weights }) applies the same artifact in page order and carries clef, key, meter and styles. JPEG input still needs conversion to PNG, or canvas pixels through readBitmapFromImage.

7Cheat sheet ↑

Set the host once, then use the complete workflow or its individual phases:

# edit remote-training-scripts/config.sh once
OMR_REMOTE_HOST=user@server
OMR_REMOTE_DIR=MuSemantiQ

# everything: checks, bundle, upload, both runs, download, combine and verify
npm run omr:remote:run

# or run each phase yourself
npm run omr:remote:prepare
npm run omr:remote:train
npm run omr:remote:download
npm run omr:remote:verify

Keep the selected artifact, both training manifests and logs, and the verification JSON together. They are the evidence for that candidate; the implementation alone is not an accuracy result.
